# 新方向與整體改版

## 從專案推導

作者 intent → 網站要承擔的功能與內容 → 實際受眾知道什麼、來做什麼。三者可往返修正：作者列的頁面、功能或元件是需求材料，受眾情境可能讓其中某項升權、降權、合併或刪除。資訊與視覺一起形成，不先套 wireframe、hero 與 feature sections 再補美術。

非功能性的視覺選擇應能指回 brief、既有品牌資產、真實素材、domain object 或內容本身。缺少視覺輸入時做可逆提案並說明缺什麼，不用固定配方補位，也不因沒有色票就停工。

## 先讓一個關係在畫面上成立

方向開放時，先讓一個關鍵關係在可渲染畫面成立，例如物件與比較資料、作品與觀看距離、內容與操作的位置。以正常尺寸看主體與文字，以完整頁看節奏，窄螢幕重新判斷。不必等功能完成才看畫面，局部草稿也不是交付。

## 卡住時問的問題

- **視覺重心**：使用者先要看見什麼？放大它能改善理解，還是擠走操作？一排同重資訊讓眼睛無處停時，先辨認其中是否真有不同角色。
- **空間關係**：要來回比較的內容相鄰，讀完才需要的內容順接。留白可以分節、聚焦或容納圖像，本身不是品質保證。
- **圖像與文字**：先看原圖。方向、地平線、人物視線與空處決定字的位置；沒有負空間就分開排，不靠整張蓋霧救一個先決定的文字區。
- **字體與尺度**：用真實標題、數字與正文試字。工具的關鍵數據與公開頁的作品都可以是主體。
- **跨段節奏**：每段是否推進理解、比較或操作？標題與說明反覆起頭會讓讀者不斷重新定位。系列資料仍需一致，不以外型種類多寡衡量豐富度。

## 使用已認可的作品

使用者有明確肯定的相關作品時，在主要構圖定型前讀 [approved-references.md](approved-references.md) 並看實際畫面：

1. 辨認值得移用的設計關係與成立條件。「日系、柔和、圓角、某字體、sidebar」這類風格詞或元件名稱不夠。
2. 依本專案的 intent、功能、受眾、內容與素材轉譯；不適用的功能就改寫或捨棄。
3. 指出轉譯改變了哪個主要空間關係：主體尺度與位置、內容的相鄰與權重、閱讀表面交界或跨段接續。若只得到配色、字體、裝飾、圓角或小元件的變化，reference 還沒參與構圖。

沒有認可作品時不強制搜尋。方向開放、品質重要且專案證據不足時，帶著具體未解問題找少數真實作品，看完整頁面與窄版，移用判斷方法而不是品牌外型。

## 認出自己的預設

方向未指定時，模型會落回少數預設；泛泛的「避免 AI 味」只會換成另一個預設。定案前問：只知道產品類別的人猜得到這個設計嗎？把題材換掉，主要 silhouette 還適用嗎？「刻意避開某預設」也可能只是它的反面預設。

以下是目前觀察到的收斂點，用來辨認，不是禁令。brief 或素材支持時可以用，並能說出專案理由：

- 暖米白底配高對比襯線與陶土色 accent；近黑底配單一螢光 accent；報紙式細線與密欄。
- 等大圓角卡片、同一種淡陰影、漸層裝飾；大數字加小標籤與統計列的 hero；每段 fade-up 進場。
- 本 repo 2026-09 試產：無關的 brief 都選暖白加綠色系；為了避開卡片改用逐段細線；淡底加左側色線的提示框（TinyYana 已否定它作為預設提示樣式）。

介面文字的模板化問題由 SKILL.md 的介面文字規則處理。

## 首次完整 render 後

承擔身份辨識的公開頁或大型改版，做一次 generic composition 檢查：暫時忽略名稱、文案、色票與裝飾，只看主要 silhouette 和內容角色。若幾乎能原封換成無關的 SaaS、社群、作品集或活動頁，回到 intent、受眾、素材與 reference 轉譯，修改足以改變主要空間關係的部分，再由 render 判斷。

已知例：「header → 大型 hero／CTA → 話題卡格加強調面板 → 大數字證據 → 雙欄故事 → FAQ 格 → 收尾 CTA」。即使有內容跨過 hero 下緣的局部重疊，主要空間分配仍是可任意換題材的骨架。這不是元件黑名單：表格、表單、FAQ、清單等成熟慣例可共用，hero、card、stats、CTA 依用途也能成立。

## 試作與取捨

對自己的意圖找反證：說某張圖是主體，它是否被標題重量或周圍空間削弱？說有節奏，是否只是相同單元重複切段？做足以改變該關係的可逆試作，用正常尺寸與連續頁面的改前改後畫面決定去留。不固定方案數，也不以元素變少、比舊稿好或清單通過代替判斷。
