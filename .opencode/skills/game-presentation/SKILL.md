# 遊戲呈現

從玩家此刻看哪裡、判斷什麼、能做什麼，決定場景與介面。先辨認是構圖、素材、讀取狀態還是操作回饋的問題；不要把「更像遊戲」直接翻成更寫實、更多粒子或更厚重的 UI。

## 形成可執行的視覺方向

用已有 brief 與畫面建立一段簡短風格描述，涵蓋媒材、輪廓／線條、色彩角色、光線氣氛及鏡頭角度。素材各自繪製或生成時，共用這些決策。

- 按角色配色：背景安靜、可操作物件突出、危險訊號可辨。色系一致不等於全部物件用同一種亮度。
- 細節量依使用者方向決定。簡單線條需要好的剪影、比例與留白；大量材質不會自動提高品質。
- 字體按用途選，兼顧語言與實際尺寸；地名、控制、數值可以有不同職責。不要為了套常見模板自動選某個字族。
- 已有明确方向就繼續；只有實際會改變結果的風格歧義才澄清。不要給每次局部修正新增批准 gate。

## 讓畫面承載遊玩

遊戲世界是正常遊玩時的主體。先安排相機、物件比例、可操作範圍與注意力落點，再安排 HUD。

- 持續可見的資料只放當下決策需要的部分。任務詳情、研究、背包與長說明按需展開。
- 基地建設、戰鬥與選單可以有不同的資訊密度，不強迫所有遊戲用滿版 canvas 或同一套 HUD。
- 若去掉遊戲名稱後像一般管理網站，檢查常駐側欄、等重卡片、大頁首是否取代了遊戲空間；改主要構圖，不只換色或加背景圖。
- 看起來可點的物件要有可見回應；選中、不能使用、缺料、受擊與完成應各自能讀懂。資訊層說明原因與下一步。
- 介面適合文字／表單時保留 DOM 或引擎成熟 UI；世界、碰撞、鏡頭與動態用既有遊戲引擎。

## 素材與操作回饋

新增或重做素材時，讀 [素材一致性](references/assets.md)。不要因有生圖工具就把可編輯的向量素材換成 bitmap。

動作已有規則但欠缺重量時，從短暫的形變、命中位置、局部粒子、音效或鏡頭反應選少量互補回饋。強度依事件意義調整，返回靜止狀態；不能掩蓋目標、阻塞輸入或修改 authority／simulation clock。

Phaser 的 input、resize、顯示層與 feedback 問題，讀 [Phaser 呈現與驗證](references/phaser.md)。其他引擎保留相同判斷，再查該引擎既有 API；不為套 skill 換引擎。

## 以遊玩畫面驗證

在真實 runtime、正常尺寸看完整構圖，再操作會改變狀態的動作。手機要重驗資訊與可點範圍，不只確認沒有水平捲軸。動態在觸發時與回到靜止後都要看，避免只截到閃光中或只看靜態美術。

沿用仍有效的檢查，只補本次變更的缺口。玩家覺得不好看時，測試通過不能代替視覺接受。回報已觀察的改善與未驗證部分。
